# 🔎 Отбор признаков в Sber-AmazMe-FMLib

## 🎨 Дизайн

`fmlib.feature_selection` сокращает набор признаков перед обучением головы модели.
Исходные данные лежат в Spark, но ни один селектор не обучает модель распределённо:
Spark используется для проекции и стратифицированного сэмплирования, после чего
ограниченная выборка материализуется в `pandas` и всё дальнейшее считается на драйвере.

Пайплайн — один цикл в [`runner.py`](../fmlib/feature_selection/runner.py) по корневому
`order`. Каждый шаг помечает решения тегом стадии из реестра методов:
`preprocessing` / `statistics` / `model` / `precise`. Кандидаты сужаются после шага;
у выброшенного признака в `FeatureDecision` видно, на каком шаге, каким методом и
по какому порогу его убрали.

Повторы одного метода с разными параметрами разрешены. После шага скоры лежат в
`result.scores["{method}#{step_index}"]` (например `null_rate#0`, `null_rate#3`),
а JSON артефакта — `{step_index:02d}_{stage}_{method}_results.json`.

- **preprocessing** — ручные исключения из файла, срез строк, случайное прореживание
  признаков для тестовых прогонов;
- **statistics** — дешёвые пофичевые фильтры без модели: пропуски, константы,
  низкая дисперсия, корреляции, PSI, Information Value;
- **model** — модельный селектор: `lightgbm` или `catboost_rfe` (можно несколько
  раз в `order`);
- **precise** — необязательный финальный отбор: `boruta_shap`.

## 🧩 Запуск

```python
from fmlib.feature_selection import (
    FeatureSelectionConfig, FeatureSelectionPipeline, FeatureSchema,
)

config = FeatureSelectionConfig.from_yaml(
    "examples/configs/feature_selection/pipeline_catboost_rfe.yaml"
)

schema = FeatureSchema(
    target="target",
    time="month_part",          # нужна для out-of-time сплита и PSI
    categorical=[...],
    continuous=[...],
)

result = FeatureSelectionPipeline(config).fit_select(
    spark,
    schema=schema,
    datasets={"train": train_df},
    output_dir="runs/exp1",
)

result.selected          # итоговый список признаков
result.dropped           # кто выпал, на каком шаге и почему
```

`spark` обязателен позиционно, но типизирован утиным способом — жёсткой зависимости
от `pyspark` в модуле нет.

> ⚠️ **Передавайте только `{"train": ...}`.** Форма `fit_select(data=df, ...)`
> возвращает весь фрейм как train: `schema.split` проверяется, но строки по нему
> **не фильтруются**. Если в одном фрейме лежат все три сплита, селекторы будут
> считать статистики на train+valid+test. Подробности ниже, в разделе про ограничения.

## ⚙️ Конфиг

### Корневой `order`

Состав, порядок и повторы шагов задаются списком `order`. YAML грузится через
`OmegaConf.load(..., resolve=True)`: ссылки `${null_rate.wide}` резолвятся без
`hydra.compose`. После resolve каждый элемент — одноключевая мапа
`метод → параметры`. Инлайн без ссылки тоже ок: `- null_rate: {threshold: 0.95}`.

```yaml
order:
  - feature_drop: ${feature_drop.default}
  - null_rate: ${null_rate.wide}
  - lightgbm: ${lightgbm.pass1}
  - null_rate: ${null_rate.tight}    # повтор с другими параметрами
  - boruta_shap: ${boruta_shap.default}

feature_drop:
  default: {path: drops.txt, strict: false}

null_rate:
  wide: {threshold: 0.99}
  tight: {threshold: 0.90}

lightgbm:
  pass1:
    n_folds: 5
    n_jobs: -1
    seed: 17            # опционально; нет ключа → execution.seed
    lgbm_threshold: 0.85

execution:
  seed: 42              # дефолт на весь пайплайн
```

`params.seed` у шага читается так же, как `params.n_jobs`: ключ рядом с остальными
параметрами метода (в том числе во вложенных `model.params` / `precise.params`).
Нет ключа — берётся `execution.seed`. В `optuna_params` сид не кладут.
`study.optimize` всегда идёт с `n_jobs=1`. Бит-в-бит не обещаем при
`n_jobs != 1` у модели и на GPU CatBoost.

Корневые ключи-каталоги (`null_rate`, `lightgbm`, …) — пресеты для `${}`; они не
ошибка. Если метода нет в `order`, он не запустится, даже если пресет описан.

Если ключа `order` **нет**, шаги собираются из старого вида:
`preprocessing.*.enabled`, `statistics.order`, `model.enabled`/`method`,
`precise.enabled`/`method`. Если `order` **есть** — он единственный источник шагов,
флаги `enabled` игнорируются. Вложенный `statistics.order` по-прежнему список
уникальных имён и нужен только этой совместимости.

Готовые примеры: [`pipeline_catboost_rfe.yaml`](../examples/configs/feature_selection/pipeline_catboost_rfe.yaml)
и [`pipeline_lightgbm.yaml`](../examples/configs/feature_selection/pipeline_lightgbm.yaml).

### Модельные и precise-шаги

Параметры модельного шага — это `params` плюс опционально `selection` и
`cross_validation` (как у вложенного `model:`). Ссылка `${model}` на весь блок
тоже работает: `enabled` и `method` из мапы выкидываются. Для `boruta_shap`
обычно ссылаются на `${precise.params}`.

```yaml
order:
  - catboost_rfe: ${model}
  - boruta_shap: ${precise.params}

model:
  enabled: true          # игнорируется, если есть корневой order
  method: catboost_rfe
  params: {...}
  selection:
    max_features: 200

precise:
  enabled: true
  method: boruta_shap
  params: {...}
```

## 🧪 Модельные селекторы

| | `catboost_rfe` | `lightgbm` | `boruta_shap` |
|---|---|---|---|
| стадия | model | model | precise |
| категориальные | **оценивает** (`cat_features`) | пропускает без решения | пропускает без решения |
| критерий отбора | до `selection.max_features` | кумулятивные пороги (`aggregated` или `vote`) | статистический тест против теневых признаков |
| `selection.max_features` | используется | **не читается** | не читается |
| eval для Optuna | **out-of-time** по `schema.time` | случайный 80/20 | случайный 80/20 |
| блок `parameters` | обязателен | необязателен | необязателен |
| стоимость растёт от | признаков и итераций | признаков и фолдов | **строк** (SHAP по каждой) |

### `catboost_rfe`

Единственный селектор, оценивающий категориальные признаки, и единственный, который
меряет **перенос на будущее**: выборка режется по `schema.time`, последние
`eval_months` периодов идут в eval, всё раньше — в обучение. Внешние `valid` и `test`
не читаются вовсе, поэтому остаются пригодны для непредвзятой проверки набора.

Дефолтное пространство поиска берётся из
`utils/default_model_param_spaces.py`, если тюнинг включён и в `parameters` нет
ни одной мапы. `params.parameters` по-прежнему нужен для скаляров вроде
`iterations` и `loss_function`.

### `lightgbm`

Обучает по одной модели на каждый внешний фолд. `optuna_mode: global` подбирает
параметры один раз, `per_fold` — независимо на каждом фолде.

Отбор признаков зависит от `model.params.selection_mode`:

- `aggregated` (дефолт) — усредняет split-важности и SHAP по фолдам, режет каждый
  канал своим кумулятивным порогом (`lgbm_threshold` / `shap_threshold`) и
  оставляет пересечение.
- `vote` — в каждом фолде тот же кумулятив считается отдельно по split и по SHAP
  (`2 * n_folds` наборов). Признак остаётся, если попал в долю не ниже
  `min_set_share` этих наборов. `min_set_share: 1.0` — должен быть во всех.

### `boruta_shap`

Сравнивает важность признака с его перемешанной копией. Стоимость определяется
**строками**, а не признаками: на каждой из `boruta_trials` итераций считается SHAP
по всей выборке. Сокращение числа признаков стадию почти не ускоряет — режьте
`max_rows`.

## 🎯 Optuna: единый контракт

Все три метода настраиваются одинаково. Общая механика лежит в
[`utils/optuna_space.py`](../fmlib/feature_selection/utils/optuna_space.py).

### Два блока с разными задачами

```yaml
params:
  parameters:        # ЧТО подбирать у модели
    depth:
      type: int
      min: 4
      max: 8
    iterations: 3000

  optuna_params:     # КАК подбирать
    enabled: true    # false — сразу обучение на скалярах, без Optuna
    n_trials: 20
    n_startup_trials: 10
    sampler: TPE     # TPE | RANDOM | GRID
    timeout: 3600    # секунды или null
```

### Когда запускается Optuna

Флаг `optuna_params.enabled` (по умолчанию `true`) включает тюнинг.
Пространство поиска выбирается так:

| Ситуация | Что происходит |
|---|---|
| `enabled: false` | Optuna не запускается, в модель идут только скаляры |
| `enabled: true`, в `parameters` нет ни одной мапы | берётся fallback из `utils/default_model_param_spaces.py` целиком; скаляры выкидывают одноимённый ключ из сетки |
| `enabled: true`, есть хотя бы одна мапа | это вся сетка пользователя; дефолтный файл не подмешивается |

Мапа `{type: int, min: 4, max: 8}` — ячейка сетки. Скаляр `3000` уходит в модель как есть.

Зафиксированный скаляром параметр исключается из пространства поиска. Без этого
Optuna продолжала бы предлагать по нему значения, и предложенное перекрывало бы
заданное — конфиг выглядел бы применённым, а на деле игнорировался.

### Синтаксис спецификации

```yaml
type: int          + min/max     → целые в диапазоне
type: float        + min/max     → дробные (+ log: true для лог-шкалы)
type: categorical  + values      → выбор из списка
values             без type      → то же, сокращение
```

`type` никогда не игнорируется: `values` вместе с `type: int` — ошибка, потому что
у Optuna нет способа перебрать список иначе, чем `suggest_categorical`.

### Дефолтные диапазоны

У `lightgbm`, `catboost_rfe` и `boruta_shap` fallback-сетки лежат в
[`utils/default_model_param_spaces.py`](../fmlib/feature_selection/utils/default_model_param_spaces.py).
Они используются **только** если тюнинг включён и в YAML нет ни одной мапы.
Любая мапа полностью заменяет fallback: незаданные ключи из Python не
добираются.

### Что происходит за один трайл

```
1. TPE предлагает значения по search_space
2. они мержатся с зафиксированными скалярами
3. добавляются служебные ключи (random_seed, verbose)
4. модель обучается на fit-части
5. считается ROC-AUC на eval-части
6. число возвращается Optuna
```

Подобранные параметры уходят в отбор — то есть **Optuna подбирает модель, которой
потом делается отбор признаков**, а не подбирает признаки.

### Как подключить новый метод

Четыре функции покрывают весь цикл, копировать разбор не нужно:

```python
from fmlib.feature_selection.utils.optuna_space import (
    build_sampler, resolve_optuna_settings, resolve_tuning_space,
    suggest_parameter,
)

settings = resolve_optuna_settings(params.get("optuna_params", {}), method_name="my_method")
fixed, space = resolve_tuning_space(
    params.get("parameters", {}),
    defaults=MY_DEFAULTS,
    enabled=settings["enabled"],
    method_name="my_method",
)
```

Новый метод сразу получает тот же синтаксис конфига, те же дефолты, те же тексты
ошибок и поддержку трёх сэмплеров.

## ⚠️ Известные ограничения

Проверено на текущей версии кода. Обходные пути указаны там, где они есть.

### Утечка теста в отбор через PSI

`PsiSelector` берёт `datasets["train"]` как baseline и `datasets["test"]` как actual.
Ключ `valid` не читается **никогда, ни в одном режиме**.

| Что передали | `mode` | Что реально считается |
|---|---|---|
| `train, valid, test` | любой | **train vs test — утечка** |
| `train, test` | любой | то же |
| `train, valid` | `train_valid` | **ничего**: всем признакам `psi=0.0, keep=True` |
| `train, valid` | `month_over_month` | последние месяцы train против ранних — как задумано |
| `train` | `month_over_month` | то же, корректно |

Переданный `test` **молча отменяет** `month_over_month`. Второй режим опасен тем,
что не падает, а тихо пропускает все признаки — в отчёте это выглядит как «PSI
посчитан, всё стабильно».

**Обход:** не передавать `test` в `datasets=`. Для `month_over_month` достаточно `{train}`.

### PSI роняет прогон на строковых категориальных

`approxQuantile` вызывается по всем кандидатам без фильтрации по типу:

```
IllegalArgumentException: Quantile calculation for column ... with data type
StringType is not supported
```

Критично именно в связке с `catboost_rfe` — он единственный, кто вообще доводит
категориальные до модельной стадии.

### Утечка в режиме одного DataFrame

`fit_select(data=df, ...)` возвращает `{"train": df}` целиком. `schema.split`
проверяется, но фильтрации по нему нет нигде в модуле.

**Обход:** использовать только `datasets={"train": ...}`.

`catboost_rfe` в обеих историях чист: читает только `datasets["train"]` и режет его
по времени внутри себя.

### Прочее

- **`low_variance` при `scale_method: standard` не работает** — z-оценка делает
  дисперсию равной 1 для всех колонок, порог перестаёт на что-либо влиять.
  Нужен `minmax` или `robust`.
- **`correlation` берёт первые `max_rows` строк** через `.limit()`, а не случайную
  выборку. На данных, партиционированных по времени, это первые месяцы.
- **`boruta_shap` молча отбрасывает категориальные.** Сколько признаков стадия
  реально оценила, видно в `result.scores["boruta_shap#<step>"]`.
- **`cross_validation.strategy`** принимает `group` и `time_based`, но реализована
  только `stratified`.
- **`execution.local_memory_limit` и `allow_local_fallback`** объявлены в схеме и
  нигде не используются — защиты от OOM на драйвере нет.
- **ML-зависимости не объявлены в `pyproject.toml`** — `catboost`, `lightgbm`,
  `optuna`, `shap`, `scikit-learn` грузятся ленивыми импортами с внятной ошибкой.
  Свежая установка библиотеки даст падение на первом же запуске отбора.
- **Пакет `BorutaShap` несовместим с numpy ≥ 2.0 и scipy ≥ 1.12** (`np.NaN`,
  `binom_test`). Пока спасает пин `numpy = 1.26.4`.

# 📊 Рабочие заметки: как читать результаты и сокращать стоимость

Раздел собран из практики прогонов на реальных датасетах и относится к
[`benchmark/`](../fmlib/feature_selection/benchmark/), а не к самому пайплайну отбора.

## Метрики бенчмарка

### Как устроен прогон

Optuna подбирает параметры на `train` → `valid`. С лучшими параметрами обучаются
модели по фолдам **внутри train**, предсказания усредняются, ансамбль оценивается
на `test`.

### Справочник

| Метрика | Данные | Как считается | Годится для сравнения |
|---|---|---|---|
| `ensemble_test_auc` | test | усреднить предсказания → один AUC | **главная** |
| `delta_test_auc_vs_baseline` | test | разность с baseline на тех же фолдах | **главная** |
| `test_auc_std_diagnostic` | test | разброс AUC отдельных фолд-моделей | как оценка шума |
| `test_auc_mean_diagnostic` | test | AUC каждой модели → среднее | справочно |
| `ensemble_valid_auc` | valid | усреднить предсказания → AUC | нет, смещена |
| `best_tuning_valid_auc` | valid | лучший трайл Optuna | нет, смещена |
| `validation_auc_mean` | **отложенный фолд внутри train** | среднее по фолдам | нет, смещена |
| `validation_auc_std` | **отложенный фолд внутри train** | разброс по фолдам | как оценка шума |

### Что важно не перепутать

**`validation_auc_*` считается не на `valid`.** Это AUC на отложенном фолде внутри
train — том самом, по которому шла ранняя остановка. Для внешнего `valid` есть
отдельная `ensemble_valid_auc`.

**`test_auc_mean_diagnostic` и `ensemble_test_auc`** считаются на одних данных по
одному массиву предсказаний. Разница только в моменте усреднения:

```
test_auc_mean_diagnostic = среднее(AUC₁, AUC₂, AUC₃)     ← среднее метрик
ensemble_test_auc        = AUC(среднее(p₁, p₂, p₃))      ← метрика среднего
```

Второе почти всегда выше: ошибки моделей частично гасят друг друга. Поэтому первое
помечено в коде как `_diagnostic`.

### Почему три метрики смещены вверх

- `best_tuning_valid_auc` — максимум по `n_trials`, и по этому же `valid` подбирались
  параметры. Максимум шумной величины завышен, причём по-разному для разных наборов.
- `ensemble_valid_auc` — тот же `valid`, уже использованный для подбора.
- `validation_auc_mean` — модель по этому же фолду решала, когда остановиться.

Все три отвечают на вопрос «насколько хорошо подогнались», а не «насколько хорошо
обобщаем».

### Как интерпретировать

1. **Смотреть на `delta_test_auc_vs_baseline`** — единственное честное число:
   `test` не участвовал ни в обучении, ни в подборе, ни в ранней остановке.
2. **Сверять дельту с `test_auc_std_diagnostic`.** Брать **больший** из двух —
   у baseline и у подхода он свой.
3. **Смотреть на `feature_count` как на вторую ось.** Цель отбора обычно не рост AUC,
   а сокращение набора без потери качества: дельта −0.001 при сокращении с 2495 до
   187 признаков — это успех.

Оговорка: `test_auc_std_diagnostic` — разброс **отдельных моделей**, а не погрешность
ансамбля. Ансамбль устойчивее, поэтому правило одностороннее: дельта превысила
границу — эффект скорее реален; дельта ниже — *не доказано*, но и не опровергнуто.

**Если дельты на уровне тысячных**, сравнивать пофолдово — фолды у baseline и подхода
общие:

```python
base = json.load(open("<датасет>__baseline.json"))["metrics"]["fold_test_auc"]
appr = json.load(open("<датасет>__<подход>.json"))["metrics"]["fold_test_auc"]
deltas = [a - b for a, b in zip(appr, base)]
```

Все дельты одного знака — эффект устойчив; скачут через ноль — различия нет.

### Повторные прогоны с разными сидами

Для честного сравнения наборов одного прогона мало: `execution.seed` (или
`params.seed` шага) управляет сэмплом, фолдами, сэмплером Optuna и внутренними
сидами бустинга. Повторы нужны, когда дельта сопоставима с
`test_auc_std_diagnostic`. Если дельта заметно больше — эффект виден и без них.

## Стоимость отбора

Разбор реального прогона: `catboost_rfe` + `boruta_shap`, ~1026 кандидатов на входе
в модельную стадию.

```
Optuna · RFE       5:09   47%
BorutaShap fit     5:05   46%
RFE (10 шагов)     0:36    5%   ← собственно отбор
Optuna · Boruta    0:06
                  ─────
                  10:56
```

Полезной работы — 36 минут из одиннадцати часов.

### Почему Optuna в RFE долгая

Каждый трайл — полное обучение CatBoost на всех признаках. Разброс времени
пятнадцатикратный (1:53 … 30:40 на трайл), и определяют его два параметра:

- **`learning_rate < 0.03`** — 5 трайлов, **37%** времени, ни один не выиграл.
  Малый шаг требует больше деревьев, ранняя остановка обрывает их поздно.
- **`depth ≥ 7`** — 6 трайлов, **42%** времени.

Лучший результат нашёлся на 11-м трайле, через 52 минуты; следующие три часа
улучшений не дали.

### Почему BorutaShap считался 5 часов

Стоимость определяется **строками**. На каждой из 50 итераций считается SHAP по всей
выборке: при `max_rows: 700000` это ~365 секунд на итерацию. Сокращение числа
признаков стадию почти не ускоряет.

### Теряем ли в качестве при укороченном подборе

**Нет.** На выходе стадии — **список признаков, а не модель**. Обученная модель
выбрасывается, бенчмарк подбирает гиперпараметры заново. Значит вопрос не «станет ли
модель хуже», а «изменится ли порядок важностей» — а он к точности настройки
существенно менее чувствителен.

Цифры того же прогона:

```
разброс AUC по 23 трайлам Optuna       0.017
разброс кривой RFE по числу признаков  0.025
```

Точка отсечения влияет сильнее, чем весь подбор гиперпараметров, — а времени на неё
тратилось в восемь раз меньше.

**Не до нуля:** совсем недообученная модель даёт шумные важности, 12–15 трайлов
сохраняют полезную часть. Проверить на своих данных: прогнать с `n_trials: 12` и
сравнить список с прежним. Пересечение 90%+ — длина подбора не важна.

### Что менять в конфиге

| Параметр | Было | Стало | Эффект |
|---|---|---|---|
| `model.params.optuna_params.n_trials` | 50 | 15 | главный рычаг |
| `learning_rate.min` | 0.01 | 0.03 | −37% времени подбора |
| `depth.max` | 8 | 6 | −20% времени подбора |
| `feature_selection_params.steps` | 20 | 10 | вдвое короче RFE |
| `precise.params.max_rows` | 700 000 | 100 000 | Boruta: 5 ч → 15 мин |
| `precise` → `boosting_type` | перебор | `gbdt` или `goss` | исключает медленный `dart` |
| `correlation.max_rows` | 500 000 | 200 000 | матрица N×N считается быстрее |

Итого: **~11 часов → ~1.5 часа**.

Отдельно:

- **`iterations` не трогать.** Ранняя остановка обрывала обучение на 790…2052
  итерациях, потолок 3000 не достигался ни разу.
- **`dart` в Boruta.** По умолчанию `boosting_type` перебирается среди
  `gbdt / dart / goss`. `dart` пересчитывает предсказания после каждого дерева и
  работает в 3–5 раз медленнее; если Optuna его выберет, все итерации Boruta пойдут
  с этим замедлением. Фиксируется скаляром:

  ```yaml
  parameters:
    boosting_type: gbdt
  ```
