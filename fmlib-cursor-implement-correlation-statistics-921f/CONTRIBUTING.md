<a name="contributing-to-fmlib"></a>
# 🤑 Внесение вклада

Вы можете:

- Отправить изменения напрямую через создание [PR](https://df-bitbucket.ca.sbrf.ru/projects/AMAZMEFM/repos/sber-amazme-fmlib/pull-requests).
- Описать баг или запрос на изменение через связь с разработчиками библиотеки (см. раздел авторов в файле `pyproject.toml`).

Прежде чем продолжить, ознакомьтесь с нашими рекомендациями по созданию [PR](#pull-requests) и [разработке](#developing).

<a name="developing"></a>
# 💻 Разработка

Разработка любого функционала организована в отдельных ветках с соответствующими правилами о наименовании:
- *feature/feature_name* - обычная фича.
- *release/X.Y.Z* - релизная ветка (см. [версионирование](#versioning)).
- *fix/fix_name* - исправление ошибок.
- *hotfix/hotfix_name* - быстрое исправление критических ошибок.

<a name="style-guide"></a>
# 🐱‍💻 Руководство по стилю
## Автоматическая проверка
Убедитесь, что у вас настроена правильная конфигурация стиля. Конфигурация расположена в файле ruff.toml.
Для автоматической проверки качества кода запустите:
```bash
ruff check .
```

## Тестирование
Прежде чем создавать PR, запустите unit-тестирование и убедитесь, что все тесты пройдены:
```bash
pytest .
```

**Примечание:** Если вы разрабатываете новую функциональность, то добавьте новые unit-тесты для них.
**Примечание:** Настоятельно рекомендуется использовать переменные окружения для ускорения процесса:
```bash
OMP_NUM_THREADS=16 pytest .
```

## Очистка ноутбуков
В силу того, что внутри ноутбуков может отображаться чувствительная информация мы имплементировали дополнительные
скрипты для очистки ячеек. Их можно применить вручную или воспользоваться [прекоммитами](#pre-commits).
```bash
python3 scripts/clean_up_notebooks.py path/to/notebook1.ipynb path/to/notebook2.ipynb ...
```

**Примечание:** Чтобы избежать случайного повреждения ноутбуков, неочищенные версии будут скопированы:
`path/to/notebook.ipynb -> path/to/notebook.unclean.ipynb`.

<a name="pre-commits"></a>
## 🤖 Прекоммиты
Механизм пре-коммитов реализует подобие CI для локального запуска. 
Эти скрипты могут запускаться в ручную или при коммите/пуше в репозиторий:
```bash
pre-commit run --all-files
```

На текущий момент оно состоит из следующих шагов:
- Проверка `.py` файлов при помощи `ruff`
- Форматирование этих файлов при помощи `ruff`
- Очистка ноутбуков
- Прогон тестов (только на пуше)

Установка прекоммитов и их обновление осуществляется через добавление
файла и комманду `pre-commit`:
```bash
git add .pre-commit-config.yaml
pre-commmit install
```

<a name="pull-requests"></a>
## 👀 Pull Requests
Для того, чтобы внести изменения необходимо:
1. Покрыть код unit-тестами. Тесты расположены внутри каждого модуля
2. Если вы вливаете большую фичу, то предоставьте пример использования в папку `examples/`.
3. [Задокументируйте](#writing-documentation) ваш код.
4. [Создайте PR](https://df-bitbucket.ca.sbrf.ru/projects/AMAZMEFM/repos/amazmefmlib/pull-requests) в `master` ветку. Название и описание PR должны быть понятны как разработчику, так и ревьюверу.
Нет потребности использовать английский язык, вы можете свободно использовать русский.
Префикс названия ветки может принимать следующие значения:
- `fix/`
- `hotfix/`
- `feature/`
5. Убедитесь, что все этапы CI пройдены (если CI настроен).


<a name="writing-documentation"></a>
# 📑 Написание документации
Мы придерживаемся стандартного подхода к написанию документации - каждый публичный класс и публичная функция должны содержать описание работы, принимаемые аргументы и формат возвращаемого значения. 

Для большего понимания, ознакомьтесь с любым публичным классом из библиотеки (например, [ParquetDataset](fmlib/data/io/parquet_dataset.py))

<a name="versioning"></a>
# 🔢 Версионирование
Мы придерживаемся стандартного подхода к версионированию библиотеки - [Semver](https://semver.org/lang/ru/).

При указании версии МАЖОРНАЯ.МИНОРНАЯ.ПАТЧ следует учитывать:
1. МАЖОРНУЮ версию, когда сделано обратно несовместимые изменения API
2. МИНОРНУЮ версию, когда вы добавляете новую функциональность, не нарушая обратной совместимости
3. ПАТЧ-версию, когда вы делаете обратно совместимые исправления.

<a name="release-process"></a>
# 💥 Релизный процесс

Для создания релизного пакета необходимо:

1. Создать ветку с префиксом *release/* с указанием версии по [правилам версионирования](#versioning)
2. Запустить Jenkins-джобу, которая опубликует пакет в Nexus
3. После прохождения Jenkins-джобы со статусом `SUCCESS` убедитесь в существовании пакета в Nexus. Если пакет опубликовался, то необходимо наложить ограничения на внесение изменений в релизную ветку. Это необходимо для того, чтобы код внутри пакета Nexus полностью соответствовал релизной ветке в репозитории.
