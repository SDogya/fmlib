# Бенчмарк отбора признаков на открытых данных

Прогоняет `fmlib.feature_selection` на публичных датасетах и отвечает на вопрос,
который по артефактам пайплайна не виден: **сколько качества стоит сокращение
набора признаков**.

Каждый прогон меряет три вещи вместе:

| | что меряем | зачем |
|---|---|---|
| **цена** | wall clock и пиковый RSS | влезаем ли в бюджет 8 CPU / 50 GB |
| **сжатие** | сколько признаков осталось | ради чего всё затевалось |
| **качество** | ROC-AUC LightGBM на `test` | не потеряли ли сигнал |

Третье измерение — ключевое. Пайплайн, который срезал половину признаков и
потерял 0.002 AUC, полезен; пайплайн, который срезал столько же и потерял 0.05,
вреден, и отличить их можно только downstream-моделью.

`test` не передаётся в `fit_select` вообще — он существует только для оценки.

## Запуск

```bash
# окружение (см. docs/environment.md)
source .venv/bin/activate
export JAVA_HOME=$HOME/.sdkman/candidates/java/17.0.13-tem   # только для Spark-тестов
export OMP_NUM_THREADS=8 MKL_NUM_THREADS=8

# 1. подготовить данные (скачивание с OpenML, кеш в parquet)
python -m benchmarks.open_data.datasets --all

# 2. прогнать свип
python -m benchmarks.open_data.run_benchmark \
    --datasets madelon synth_wide kdd09_appetency \
    --pipelines cheap full \
    --tag my_run
```

Результаты пишутся в `benchmarks/open_data/results/<tag>.{json,csv}`, а
промежуточные артефакты пайплайна — в `results/<dataset>/<pipeline>/`.

Кеш данных лежит в `$FS_BENCH_DATA` (по умолчанию `~/rusakov/data/fs_benchmark`)
и в репозиторий не попадает.

## Датасеты

Лестница по двум осям, которые важны для отбора: число строк и число колонок.

| датасет | строк (train) | признаков | чем интересен |
|---|---:|---:|---|
| `madelon` | 1 560 | 500 | классика FS-бенчмарков: сигнал примерно в 20 колонках из 500 |
| `bioresponse` | 2 250 | 1 776 | самый широкий реальный: p ≫ n |
| `synth_wide` | 72 000 | 602 | **известный ответ**: 40 информативных, 30 дрейфующих |
| `kdd09_appetency` | 30 000 | 207 | ближе всего к банковскому профилю: смешанные типы, 70% пропусков, 1.8% таргета |
| `santander` | 120 000 | 201 | 200k строк × 200 анонимных числовых |
| `porto_seguro` | 357 127 | 57 | самый большой по строкам, реальная смесь категориальных |

### Про колонку `month_part`

Ни в одном открытом датасете нет пригодной оси времени, поэтому месяц
назначается случайно. Это осознанное решение, и читать его нужно правильно:
**на реальных датасетах PSI и out-of-time сплит меряют свою цену, а не пользу** —
дрейфа там нет, находить нечего.

Исключение — `synth_wide`: в нём 30 колонок с именами `drift_*` сдвинуты на
3σ в последних месяцах, а 40 колонок `inf_*` действительно информативны. Это
даёт ground truth сразу для двух вопросов: находит ли пайплайн сигнал
(`informative_recall`) и выбрасывает ли он нестабильные признаки
(`drifting_kept`).

## Пайплайны

| конфиг | состав | что проверяет |
|---|---|---|
| `cheap` | null_rate → constants → low_variance → correlation → iv | пол по стоимости: моделей нет вообще |
| `cheap_psi` | то же + psi (month_over_month) | цена PSI и его польза на `synth_wide` |
| `lightgbm` | только модельная стадия | что добавляет LightGBM+SHAP сам по себе |
| `full` | статистики → psi → lightgbm | рекомендуемая форма: дешёвое раньше дорогого |
| `full_boruta` | full → boruta_shap | стоит ли precise-стадия своего времени |

Optuna везде выключена намеренно: иначе сравнение съезжает с «какой отбор
лучше» на «кому повезло с гиперпараметрами».

## Как читать результаты

* `kept_%` — сколько признаков осталось;
* `auc_delta` — разница с baseline (все признаки) на `test`; **отрицательное
  значение — это потеря качества**;
* `select_s` / `peak_rss_gb` — цена отбора;
* `informative_recall` / `drifting_kept` — только для `synth_wide`.
